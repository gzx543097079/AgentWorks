# 桌面 Agent 内部接口

仅供总控 Agent 阅读，用户使用自然语言。桌面会话通过自己的代码执行工具调用这里的 Python 库；它只管理本地状态，不启动模型进程、发送请求或读取模型凭证。当前本地支持 macOS/Linux、Python 3.9+、Git，Python 只用标准库。

## 初始化与接续

在仓库根目录的代码环境中：

```python
from agentworks.desktop import Workspace

team = Workspace()
team.check()        # 角色数量、工作流数量、适配文件是否需要同步
team.status()       # 已有项目；不要重复创建
team.status("first-opportunity")
```

桌面端采用工作树或不同副本时，用 `Workspace(data_dir="原数据目录的绝对路径")` 指向同一份数据；每次调用沿用该路径。不把原机路径硬编码进仓库。

安装在产品仓库时，在该仓库根目录先 `sys.path.insert(0, ".agentworks/engine")` 再导入。`Workspace()` 自动以该仓库为产品工作区、以 `.agentworks/` 为数据目录；`check()` 返回 `embedded: True`，并核对安装文件有无改动。此模式只允许一个项目，简报、记忆和输入资料位于 `docs/项目简报.md`、`docs/项目记忆.md`、`docs/inputs/`，各任务只写自己的输出目录。

新项目和阶段：

```python
team.create("my-product", "海外选题", kind="compare", market="待比较", brief="先比较游戏和工具，再按盈利证据选方向")
team.plan("my-product", "discovery")
```

现有阶段重复 plan 会复用未完成阶段，前置未通过会拒绝。带 `kinds` 的任务只为对应项目类型建立；立项选定方向后用 `team.set_kind(project, "game", "原因")` 记录，后续阶段据此建立任务。可用阶段为 discovery、product、design、build、launch、growth。

## 分配给桌面原生子 Agent

```python
assignments = team.begin("my-product", host="codex-desktop", max_tasks=2)
# Claude 桌面 Code 模式使用 host="claude-code-desktop"
```

返回列表，每项含 `role`、完整任务包 `prompt`、任务包文件 `prompt_file`、交付文件 `result_file`、可原样转交的委派内容 `message` 和该次任务 `ticket`。把 `message` 交给原生子 Agent；总控保管 ticket。begin 会预先建好任务的输出目录。两个文件都在项目 `runs/` 目录内，会话中断也不会丢失交付。任务包里的依赖只含摘要和 `report_file`，执行者按需读取报告。角色固定名称：Codex 为 role 本身；Claude 为 `agentworks-` 加上将 role 中下划线替换为连字符后的名称。固定角色不可用时用通用子 Agent，完整任务包已包含角色快照。

begin 在分发前登记 running，保存任务包和交接凭据。独立只读任务每批最多3个；可写任务独占。另一会话不能领取有执行中任务的项目。批次为空时查看状态：可能阶段完成，也可能任务正在等待修复；不要误报所有工作完成。

父会话的 ticket 不需要放进给子 Agent 的任务内容。三位模拟评审各自取得同一个原型输入，不继承同轮其他评审的结果。子 Agent 按 `config/result.schema.json` 返回 JSON；使用当前桌面工具完成实际研究、实现与测试。

## 保存结果与处理失败

```python
# result_dict 是子 Agent 的真实 JSON 交付，不能为了验收通过编造。
status = team.complete("my-product", assignments[0]["ticket"], result_dict)
team.status("my-product")
```

子 Agent 已写入 `result_file` 时直接 `team.complete(project, ticket)`，库会读取并校验；通过后报告写入项目的文档目录（如 `docs/02-product/需求文档.md`），过程记录保存为 `attempt-N-result.json`，删除草稿。artifacts 必须位于任务的输出目录。已完成但缺失的报告可用 `team.publish(project)` 补写到项目目录，`plan` 和 `complete` 也会自动补写。结构错误不会自动完成任务，修正后用同一 ticket 保存。依赖、产物存在性、当前尝试和阶段 verdict 都会检查。文件存在和 Schema 通过不代表事实或实现质量已经验证。

工作进程或工具失败时，总控调用 `team.fail(project, ticket, reason)` 留下失败记录。缺少数据时可按 Schema 交付 blocked。全部批次任务都落盘后，才继续 begin；不要遗留 running 状态。

用 `team.retry(project, task_id, reason)` 重试失败、阻塞或待修改任务，每任务最多3次。重试后 begin 产生新 ticket；上一尝试的迟到结果会被拒绝。

## 用户确认与版本管理

用户关卡带 `user_confirmation: true`，不会被 `begin` 委派，也不能用 `complete`、`submit` 或 AI gate 结果放行。`status` 中的 `confirmations` 列出已具备前置条件的确认关卡；仅 `begin` 返回空列表不表示阶段完成。

```python
preview = team.review("my-product", confirmation_task_id)
# 向用户展示具体版本、实际预览、变化和待决定事项；等待明确答复。
team.confirm("my-product", confirmation_task_id, preview["digest"],
             decision="approve", feedback="用户的实际确认原话")
# 要求修改用 decision="revise"，暂缓用 decision="defer"。
```

`review` 保存文件清单、SHA-256、产品版本、依赖任务尝试及快照位置，任务进入 `awaiting_user_confirmation`。`confirm` 必须使用该快照 digest，保存用户反馈、确认人和时间；文件、目录内容或版本变化会拒绝旧 digest。`approve` 才解锁下游；`revise` 进入 `needs_revision`；`defer` 保持等待。库保存总控转录的真人决定，不能自行验证聊天身份，因此总控不得编造用户反馈。明确的历史授权仍适用于对应外部操作，但不能代替本次交付版本的必要确认。

```python
# 指定实际需要修改的上游任务，不能只重做确认关卡来绕过修订。
team.revise("my-product", source_task_id, reason="用户反馈及本轮修改范围")
```

`revise` 可指定当前有效依赖链上已经执行过的产出任务，包括较早阶段；不能指定用户确认关卡，也不能修订其他产品版本或已经归档的任务。它会重置该任务、共享同一输出目录的产出任务及受影响的下游结果、独立评审和用户批准，保留旧结果事件与文件快照。跨阶段修订会把依赖旧交付的阶段标记为 `abandoned` 并记录 `superseded` 原因；历史交付仍可查阅，但不能作为有效前置。源阶段重新通过后，后续阶段须重新 `plan`、评审和确认。开启已有阶段新一轮 `plan` 时，也会归档被替代的旧阶段及其后续阶段，不回退复用更老的批准。

`status(project)` 的 `current_stage` 是当前有效阶段编号；`stages` 包含全部历史，不能直接把列表最后一项当作当前阶段。新会话读取这个编号、任务状态、保存的 review 和 history 接续。相同内容重复 `review` 返回同一快照并保留暂缓反馈。发现已批准文件变化后，批准会持久标记失效；还原旧文件不会自动恢复批准。

每次 `begin` 保存本次任务的依赖文件指纹，`complete` 会检查任务执行期间输入是否变化；过期交付保留 running，须用原 ticket 明确 `fail` 或确认 worker 停止后恢复，再修订和重新执行。`review/confirm` 同时核对交付快照、目录内容与当前有效评审的输入，不能刷新预览绕过重新评审。设计初审修订后有独立的 `*_recheck`、`revision_triage` 和最终 QA；复评仍需修改时，对实际产出 `revise`，不沿用初版结论。

普通工具失败继续使用 `retry`，每轮最多3次尝试；revise 重置失败重试计数，交付修订号继续递增。明确交付修订不受失败重试上限限制，确认等待不属于工具失败。快照保存后若状态提交中断，内容一致的原 ticket 可以跨会话继续完成，拒绝用同一修订号覆盖不同内容。

```python
team.set_version("my-product", "0.2.0")
```

新项目默认产品版本 `0.1.0`，格式为 `major.minor.patch`。仅没有运行任务且所有阶段完成或终止时可设置新版本。已有批准仍保留其原产品版本；新版本不能直接沿用前置阶段旧版批准，需要重做相关阶段并确认。

产品版本、设计修订标签（如 `prototype-v2`、`ui-v3`）和构建编号（如 `build-007`）分别记录。库自动为每次保存的交付建立 `runs/<run>/<task>-v<attempt>/` 快照，含实际文件副本及清单；任务 `snapshot` 保存对应元数据。任务包的 `delivery_version` 给出本轮修订号与产品版本，执行者据此标注报告。用户预览另存于 `runs/<run>/<task>-review-<digest>/`。标签和构建号由交付报告注明；归档副本不覆盖、不能作为当前可写产物。后续 `begin`、`plan` 会检查当前有效批准对应的文件，变化时要求修订与重新确认。

本版不迁移旧项目数据库；保留旧数据，在新的数据目录创建项目。本版备份恢复仅支持当前格式，快照与用户确认记录随备份保留。

## 中断与修改方向

新会话查看 status 中 running 任务的 `execution`，可找到平台记录和原 ticket。如果实际交付已经完成，使用原 ticket 保存；不要为同一成果另开任务。

若原子 Agent 已经停止且交付不完整：

```python
team.recover("my-product", workers_stopped=True, reason="已确认原桌面会话和子 Agent 停止，检查了现有文件")
```

此确认由总控根据真实状态作出；库无法替桌面应用终止原生子 Agent。原任务还活跃时不能传 True。恢复后检查产物并按原因 retry。

终止阶段使用 `team.abandon(project, reason)`，有执行中任务时会拒绝。收齐交付或恢复已停止的任务后再终止，新一轮 plan 保留旧记录。

## 记忆和备份

```python
team.note("my-product", "用户确认优先英语市场，验证预算待补充")
team.history("my-product")
team.export("my-product", "用户指定的绝对备份路径.zip")
restored = Workspace(data_dir="用户指定的空数据目录")
restored.restore("备份文件的绝对路径.zip")
```

备份前必须完成或停止并恢复当前任务。备份包含可能敏感的输入、交付和日志，不读取平台全局凭证，也不包含产品 Git 历史。恢复后继续使用相同数据目录。

## 维护检查

角色源为 `config/team.json`；技能源为 `.agents/skills/agentworks/SKILL.md`。维护时由 Agent 调用同步函数，生成两平台适配：

```python
from scripts.sync_agents import synchronize
synchronize()
assert synchronize(check=True) == []
```

安装或升级到产品仓库：

```python
from agentworks.install import install
install("用户指定的产品仓库绝对路径")
```

修改内部代码后执行仓库单元测试。维护脚本不是产品运行入口，不调度模型，也不要求用户在终端使用团队。
