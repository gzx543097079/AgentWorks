# 按需求架构生成与审查

> 来源：TeamFlow `teamflow-v1.0.0`，提交 `e2088f01b7834ca1cf7217004309fe0cb22ee3bc`，原文件 `.agents/teamflow-core/references/ARCHITECTURE.md`。保留专业规范并调整资源链接；文中的 TeamFlow 专属命令/路径仅适用于已安装原工具的业务工程，不能据此声称当前仓库已安装它们。 用户当前目标、平台和既有授权优先；版本号及商店/地区规则在实际执行时重新核对。

适用于生成业务代码、功能扩展及明确的架构重构。需求已确认的架构、模块边界和依赖方案是实施约束，不用个人偏好或模板默认替换；已有需求记录和用户本次明确更正可作依据，无冲突不再次索要确认。

## 实施前定位归属与已有能力

先找工程现状里的既有架构决定，再搜索本次相关的功能、组件、工具及真实调用方。普通功能沿用现有职责和接口；只有新增或改变模块边界、依赖方向、状态所有权时，才在原需求卡或工程现状补充受影响的职责、位置和接口。

资料缺失时从相关代码核实。只有无法安全推断的关键架构取舍或决定冲突才询问，独立部分继续。已有模块索引按 [MODULE-CONTEXT](teamflow-core-module-context.md) 辅助定位；索引未变化不证明架构正确，也不默认全仓扫描。

## 模块边界与依赖

- 按业务职责和状态所有权划分模块（如账号、商品、购物袋、订单），不机械地每页一个模块。只公开真实使用方需要的入口、数据和协议。
- 跨模块只通过公开接口协作，不访问对方节点、控制器内部、私有模型或存储。组装层负责依赖和跨模块导航；功能用回调或明确契约表达导航意图。
- 依赖无环，共享层不引用具体业务功能。外部服务优先构造注入，状态来源和生命周期明确；不用服务定位器和隐式全局可变状态，不为单个场景造空协议、万能基类或无用途的 Repository/UseCase。
- 共享 UI 通过数据和回调接入，不读页面私有状态。业务规则留在所属模块或明确的领域服务，不因多处调用就放进通用工具层。
- 默认在现有工程内划分逻辑职责，不因目录变多就拆编译单元、Package 或仓库；改变实际工程结构须属于本次明确范围，并核对生成配置和资源引用。

## 复用判断

复用看业务语义、状态所有权和变化原因是否一致，不只看代码相似。

| 实际情况 | 处理方式 |
| --- | --- |
| 已有能力满足需求 | 直接复用 |
| 职责一致，仅缺少少量能力 | 扩展原实现，检查已有调用方 |
| 多处实现语义与变化原因一致 | 抽取共同能力并迁移实际使用方 |
| 代码相似，但业务规则或状态生命周期不同 | 保持独立，不用开关强行统一 |
| 只有一个实际场景 | 留在所属模块，不提前进公共层 |

共用层只放实际共用、接口内聚的能力，不把页面细节变成泛型参数、配置开关或继承层级。单个使用方因外部依赖隔离或真实独立边界也可抽取，但须说明用途，不以“将来可能复用”为依据。

## 工具类按职责收敛

| 能力 | 归属 |
| --- | --- |
| 无状态计算、格式转换 | 对应职责的函数或小类型 |
| 网络、存储、图片加载 | 基础设施服务 |
| 会话、权限、订单等业务规则 | 所属业务模块或领域服务 |
| 通用按钮、空状态与样式 | 公共 UI 层 |
| 页面专用辅助逻辑 | 页面或所属功能模块内部 |

不向 `Utils`、`CommonManager`、`BaseTool` 等万能容器堆职责，extension／category 也不做无关业务的入口。已有大工具类只拆本次涉及的职责，先搜同义能力，避免产生第二套实现。

接口写明输入输出、失败行为、线程／隔离要求和副作用。无状态工具不暗中读取当前用户、页面、网络或全局存储；有外部依赖的通过参数或构造注入。缓存、订阅、长任务和共享可变对象明确所有者与释放策略，不用新增单例掩盖归属问题。

## 抽取与迁移闭环

1. 定位重复实现和真实调用方，核对行为差异、边界条件和资源引用。
2. 确定唯一职责与接口，保留需求确认的行为，迁移本次范围内的使用方。
3. 删除已无引用的旧实现、空包装、无用配置和资源，不让旧副本继续承担同一规则；删除前检查工程配置、场景／界面配置、运行时类名和注册表引用，文本搜索无结果不足以证明无人使用。
4. 验证共同能力与受影响调用方；确需分批迁移时，在原需求卡写清剩余范围与原因，不宣称已全量收敛。

明确授权清理的内部实现可直接替换，不无故保留兼容包装。已发布公共接口、持久化数据和外部协议按实际契约判断，数据变化按[数据迁移与恢复](#数据迁移与恢复)，清理旧工具不能扩张为破坏用户数据。

## 生成后核对

按上文各节回查本次改动：职责与依赖符合已确认架构且无环、只暴露必要接口；共用能力有真实调用方，核心业务规则只有一个权威实现；范围内调用方迁移完成，删除的实现无残留引用，既有行为和失败语义没有非预期改变。另外：

- 核心输入输出与边界有独立单元验证，按影响检查取消、并发、缓存隔离、订阅和对象释放，并回归原 UI 主路径；编译通过不能证明架构或复用正确。
- 适用结果写入原需求 AC，证据只引用一份；提交时复用未变结论，只复查新增差异。没拿到的证据保留未验证。
- 范围外的既有架构问题只记录，不顺带重构全项目，也不新增全仓扫描、审批表或重复清单。

## 数据迁移与恢复

仅在持久化模型、文件格式、数据库结构或跨版本数据契约变化时加载。沿用项目既有迁移机制，不为普通功能新增迁移框架。

1. 核对实际旧版本、数据规模和存储位置；AC 写明已有用户的升级结果，卸载重装不能证明迁移成功。
2. 用脱敏样本或项目内合成数据复现旧格式，验证正常迁移、空数据、中途失败、重复执行与恢复；记录不可逆步骤。
3. 明确迁移前后的版本判断、写入原子性和幂等行为。备份只在明确位置与范围内创建；涉及项目外真实数据先取得本次明确授权。
4. 核对旧版读取新版数据的兼容性；不支持降级时写明限制，代码回退不等于数据恢复。
5. 失败时保留可定位证据并按既定方案恢复，不自行清空用户数据或扩大到生产环境。

决定与结果写入原需求卡或引用项目既有迁移说明。
