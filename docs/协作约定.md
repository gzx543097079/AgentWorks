# 团队协作与交付约定

## 角色专业标准

所有角色按20年相关经验的资深从业者标准工作：关注约束、证据、失败方式、取舍和可交付结果。角色设定不构成真实工作经历。新用户评审采用20年用户研究方法模拟第一次使用者；不会给模拟新用户附加产品先验知识。

## 游戏与工具共用的决策框架

机会比较必须包含目标市场、用户任务、现有替代、差异、付费证据、获客渠道、实现与验证成本、反面证据和下一项最小实验。不能从竞品热度直接推算利润。

游戏重点验证核心循环、反馈、回访及付费体验；工具重点验证任务完成、效率、重复使用和付费价值。小样本访谈可发现问题，不证明总体留存或盈利。商业情景统一时间窗口并标明所有假设。

## 独立评审及裁决

三位模拟评审分别代表品类熟练用户、首次使用者和关注付费价值的使用者。各自接收同一原型版本、用户任务和产品约束，不接收其他评审的判断。模拟评审类型为 `simulated` 或 `hypothesis`。真人反馈用 `templates/用户反馈.md` 记录。

反馈格式：问题所在界面或操作 → 观察证据 → 影响 → 建议 → 验证办法。产品负责人负责去重并逐条采纳、延期或拒绝，记录理由。设计师修改原型，开发者实现，独立测试者复核。

## 交付与阶段门槛

结构化结果见 `config/result.schema.json`：

- `status`：completed 或 blocked。
- `summary`：简要结果；`report`：完整可读报告。
- `verdict`：pass、revise、blocked、not_applicable。阶段最后一项必须 pass 才能进入后续阶段。
- `evidence`：来源、观察、假设、模拟或未知；每条写 source 和 note。
- `artifacts`：工作区内实际存在的文件，相对路径；正文报告由桌面总控保存。
- `next_actions`：具体下一步。

已写报告不表示产品已验证。阶段 pass 的含义取决于任务：研究 pass 是研究可交接，设计 pass 是原型符合验收；上线准备 pass 不代表已发布。真实上线与经营结果来自实际工具记录和数据。

内部模块验证交付结构、依赖与阶段状态。证据质量、设计质量和测试充分性由专业角色检查，不能把格式校验宣传为事实核验。

## 保存与恢复

单个工作流运行保存角色和任务配置快照，每次尝试保存单独任务包与原始输出。已通过的上游报告进入下游上下文，重要决策进入项目记忆。新一轮会保留历史；早期阶段更新后，下游不得继续使用已经过期的前置链。

可写角色单独执行；独立只读任务可按宿主能力并发，每批最多3个。一个项目同时只有一个桌面总控批次执行，状态变更使用项目锁。不同产品使用各自工作区、项目编号和状态记录，但本地文件布局不等于多租户安全隔离。

## 外部工具与授权

团队的业务规则不赋予额外账号权限。浏览、图像、设计、引擎、数据分析及运营连接必须在实际环境可用。缺少工具应交付可完成的部分并指出具体缺口。

单角色任务完成研究、本地实现和材料准备。真实对外操作由桌面总控按用户授权执行并保存结果。工具权限、模型和子 Agent 能力由桌面应用提供，本仓库不启动独立模型进程；角色说明不能当作第三方连接器的强制权限隔离。
