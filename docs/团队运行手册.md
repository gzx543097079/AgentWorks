# 桌面团队运行手册

供桌面总控 Agent 使用。Codex 桌面端和 Claude 桌面端 Code 模式共用 `config/team.json`、`config/workflows.json` 和项目数据。原生角色由同步脚本生成，业务内容只维护一份。

## 启动与继续

1. 用当前桌面会话的代码工具加载 `agentworks.desktop.Workspace`，读取 `status()`。内部调用参考 [桌面内部接口](桌面内部接口.md)，不要把操作转交给用户在终端执行。
2. 沿用用户指定的项目；只有一个已有项目时可直接沿用。多个候选且未指定时澄清项目。新项目用 `create` 保存目标；已有项目读状态以及工作区 `BRIEF.md`、`MEMORY.md`。不要依赖当前聊天记忆。
3. 用 `plan` 建立当前阶段。默认先比较游戏与工具，依据盈利证据选题；用户已限定游戏或工具时用对应 `kind` 创建，另一类的研究任务不会建立。discovery 验收选定方向后，先用 `set_kind` 记录游戏或工具，再 plan product。缺预算先记未知，继续可完成的研究。前置验收未通过时处理缺项，不能绕过。
4. 用 `begin(project, host, max_tasks)` 登记就绪批次，取得任务包和 ticket。默认一次一个任务；独立只读任务可按宿主能力一次准备最多3个，可写任务必须独占。不要自行增加超过宿主限制的并发。
5. 把每项的 `message` 原样作为委派内容交给当前平台对应原生子 Agent：它指向项目内的 `prompt_file` 和 `result_file`。可在其后补充用户新确认的事实，但不要另指定交付路径，不要把任务包另存到临时目录或整段粘贴进委派消息。原生角色名为 `agentworks-` 加内部角色编号（下划线转连字符），如 `technical_lead` 对应 `agentworks-technical-lead`。固定角色未加载时用通用子 Agent；ticket 由总控保存。任务包的 `skills` 是当前角色入口与本地资源指纹，先读取入口，再按实际平台与任务加载支持资料；跨角色共享引用跟随当前仓库版本。单角色执行者不再次委派、不修改进度数据库。独立评审不要继承其他评审的结论。
6. 子 Agent 交回后核对证据、文件和验收结论，用 `complete(project, ticket)` 读取 `result_file` 保存；只需读取摘要即可汇报，不必把整份交付载入总控上下文。格式错误先让执行者修正；工具或会话失败用 `fail` 留下原因。收齐本批结果后才能分发下一批。
7. 常规步骤按既有授权继续。遇到用户确认关卡，主会话展示具体交付并等待真人决定；完整产品工作授权不能跳过必要确认。重要决定用 `note` 保存，每轮汇报交付、状态和具体缺项。

## 桌面执行与工具

使用当前桌面会话的模型和子 Agent，不启动 Codex 或 Claude 的独立命令行进程，不另行管理模型登录、搜索开关或额度配置。

读取和修改文件、网页研究、绘图、浏览器检查与运行代码使用当前桌面会话实际可用的工具。实际工具权限由桌面应用控制，角色说明不构成权限隔离。缺少必需能力时明确 blocked，不虚构已搜索、已渲染或已测试。

没有子 Agent 能力时，说明顺序角色扮演不具备独立上下文。需要独立评审的任务保持 blocked，直到独立会话或真人提供反馈。没有 Python／文件访问工具时可整理材料，但不能声称项目状态已保存。

## 共用进度和中断恢复

两个桌面端指向同一个数据目录；工作树或其他仓库副本需显式指定该目录。每批任务登记后跨会话保持 running，另一会话不能重复领取。

新会话先查看状态中的 execution 信息，确认原桌面会话及子 Agent 是否仍在工作。如果已取得该次真实交付，可以使用原 ticket 保存；如果原执行已经停止但没有完整交付，用 `recover(workers_stopped=True, reason=...)` 标记中断，再按原因 retry。不要把恢复状态当作停止原子 Agent 的手段。

普通失败重试最多3次；用户要求的交付修订通过 revise 开新尝试，不受失败重试上限限制。重试会生成新 ticket；旧结果不能覆盖新尝试。改变方向时先收齐或停止并恢复当前任务，再 abandon 并保留历史，重新 plan。备份前结束当前执行，恢复使用空数据目录。

## 产品协作

角色按20年资深标准交付，不声称真实履历。三位模拟用户接收同版原型与任务，各自独立评审；AI意见标注 simulated，真人反馈、真实使用数据和经营数据单独放入输入资料目录（产品仓库中为 `docs/inputs/`）并附来源。

产品负责人逐条采纳、延期或拒绝反馈，记录理由。所有角色按 `config/result.schema.json` 交付，真实产物必须在项目中实际存在。

## 产出放在项目目录

团队产出都是项目的文件，按类别放在项目目录，可以直接提交到 Git。工作流为每个阶段定义文档目录（`docs`），为每个任务定义报告文件名（`report`）和可写目录（`outputs`）：

| 内容 | 位置 |
|---|---|
| 各阶段报告 | `docs/01-discovery/` … `docs/06-growth/`，如 `docs/02-product/需求文档.md` |
| 项目简报、项目记忆、输入资料 | `docs/项目简报.md`、`docs/项目记忆.md`、`docs/inputs/` |
| 低保真原型、可操作原型、UI 设计稿 | `design/wireframe/`、`design/prototype/`、`design/ui/` |
| 美术与动画、音频 | `design/art/`、`design/audio/` |
| 源代码 | `app/` |
| 发布配置、商店素材、获客素材、帮助内容 | `release/`、`store/`、`marketing/`、`support/` |

`complete` 保存时把报告写入项目对应文件，并按 run/task/attempt 保存报告与实际交付快照；重做保留旧快照，当前工作目录可更新，不能依赖尚未提交的 Git 作为唯一历史。其他交付（图片、表格、数据快照、配置）由执行者写入任务包的 `output_dirs`，不在输出目录内的文件会被拒绝。`.agentworks/` 保存状态库、任务包、执行凭据、用户确认记录和交付快照，不提交到 Git。每个阶段验收通过后提醒用户提交项目，或在用户授权下提交。

## 27 个角色的分工与交接

- 机会研究：市场、增长、用户研究与商业分析形成候选；协作质量角色核对证据链，总控决策。
- 产品定义：行业专家核查业务约束，产品确定范围；游戏策划统筹核心循环，关卡与数值分别给出细化方案；研究负责人定义真人实验，数据角色定义口径，产品营销定义价值表达，技术与安全角色提出实现及验收约束。
- 设计：先交 `design/wireframe/` 低保真原型，经用户确认流程后深化；美术资产保存在 `design/art/`，音频保存在 `design/audio/`；UI 制作并接入原型。评审期间冻结原型，三位模拟评审、本地化和真实用户研究各自交付。产品裁决后，素材原负责人先修订，UI 再集成；三位模拟用户、本地化和用户研究对修订版独立复评，产品复核裁决与 QA 验收后用户确认 UI，才进入开发。
- 开发：开发者实现，QA、技术负责人和安全负责人分别初审，开发者统一修复。技术和安全各自的 gate 都通过后，QA 才能进行最终验收；用户确认具体可运行构建后进入上线准备。审查者不修改待审实现。
- 上线：发布工程师准备运行方案，产品营销准备内容，销售准备适用的企业或合作试点，客户成功准备帮助与支持；增长适配渠道，本地化校对，协作质量角色审计交接，总控核对准备状态，再展示最终发布方案供用户确认。
- 运营：真实数据分析与客户反馈进入用户研究、增长和产品迭代；协作质量角色检查重复工作、来源和记忆建议，由总控保存已确认的决定。

关卡、数值只适用于游戏；美术、音频取决于产品已确认的素材需求；行业专家取决于领域要求，销售取决于企业购买方或合作模式。角色全部可用，不等于每个项目都需要产出完整的专业方案。工作流中带 `kinds` 的任务只为对应项目类型建立（如游戏项目不建工具研究，工具项目不建游戏研究；关卡、数值不为工具项目建立）。其余不适用的非 gate 任务用 `status=completed`、`verdict=not_applicable` 交付明确原因，仍通过正常 ticket 保存。缺少必需工具或数据时返回 blocked，不能当作不适用。

真人研究的准备与证据分析分别记录。产品范围需明确原型或上线前必须完成哪些真人验证；缺少必需证据时相应任务或验收阻塞。允许先准备原型时，无真人记录可以交付测试包与证据缺口，但不能声称需求已验证。研究、支持和销售角色仅准备对外材料，总控根据用户授权执行联系并记录真实结果。

美术和音频角色属于可写任务，同 UI、开发一样独占执行批次；其他新增角色为只读。协作质量角色提供建议，不修改项目状态或团队配置，也不代替产品 QA、技术与安全验收。

## 必要用户确认

| 关卡 | 先展示 | 批准后解锁 |
|---|---|---|
| `scope_confirmation` | 目标用户、核心功能、本轮范围、不做事项、产品版本 | 原型设计 |
| `prototype_confirmation` | 低保真原型图、主流程、关键状态、修订变化 | 正式美术、音频与 UI 深化 |
| `ui_confirmation` | 通过独立验收的 UI 图、可操作原型、适配效果与限制 | 开发 |
| `build_confirmation` | 可体验构建、build 编号、测试证据与已知问题 | 发布准备 |
| `release_confirmation` | 最终构建、渠道、价格、预算、具体操作与恢复方案 | 完成上线准备；外部操作仍按明确授权执行 |

这些任务带 `user_confirmation: true`，由主会话处理，`begin` 不会把它们委派给角色。前置完成后用 `Workspace.review(project, task_id)` 生成含 digest 的快照，主会话把预览、版本、变化和待决定项展示给用户。状态进入 `awaiting_user_confirmation`，与缺工具或证据的 blocked 分开。

收到用户明确意见后，用 `Workspace.confirm(project, task_id, digest, decision, feedback)` 记录决定和用户原话：`approve` 批准该快照并解锁下游；`revise` 保存修改意见、保持下游关闭；`defer` 保留现场、暂缓确认。需要实际修改时用 `Workspace.revise(project, task_id, reason)` 指定产出任务，重置该任务及下游并保留旧交付，修改后重新展示。不得把用户关卡交给子 Agent 自批，也不得用 AI 评审、QA 通过、沉默或笼统授权替代真人批准。

批准绑定具体文件快照；实际文件变化会持久记录批准失效，恢复旧文件不自动恢复批准。不能刷新预览来代替产出修订和重新评审。流程、布局、视觉风格、范围、收费或发布条件实质改变时重新确认。等待期间可继续不依赖该决定的就绪任务。共享输出目录的产出须一并重审；跨阶段修订自动归档依赖旧交付的下游阶段，重新通过源阶段后逐阶段 plan。新会话按 status.current_stage 定位有效阶段，不能用历史列表最后一项推断当前工作。

## 产品与交付版本

产品版本使用 `0.1.0`、`0.2.0`、`1.0.0`，表示功能范围；设计修订使用 `prototype-v1`、`prototype-v2`、`ui-v1`，表示某份交付的修改轮次；可运行产物另有唯一 `build-001`、`build-002` 或平台 build 编号。三者分别记录，例如“产品 0.1.0 / prototype-v3 / ui-v2 / build-007”。报告写出基准版、变化、实际文件与验证版本，不把标签当作证据。

主会话用 `Workspace.set_version(project, product_version)` 设置产品版本；默认 `0.1.0`，有运行任务或未完成阶段时不能切换。设计与构建编号由交付报告明确记录，内部 run/task/attempt 快照保存具体交付历史；已批准版本不覆盖，不依赖聊天记忆。重做必须通过 revise 或正常重试生成新尝试，不能将旧执行结果当成新交付提交。

此版不提供旧项目数据兼容或自动迁移。保留原数据，若采用此版流程则创建新项目；不能直接改旧数据库或宣称旧批准已满足新关卡。

对外消息、投放、付费和生产发布按用户明确授权执行，既有授权在其明确范围内继续有效；必要交付确认仍逐项完成。launch 只准备上线材料，真实外部操作由总控使用已连接工具执行并记录结果。

## 职责技能与规范来源

按 [职责与技能](职责与技能.md) 使用 TeamFlow 分配资源与海外 App 方法。技能规范不建立第二套状态；AC 与证据写入产品报告，主会话保存。任务包中的指纹可用于交接比较，但不会自动锁定技能内容；执行期间保持仓库检出稳定，记录提交及本地改动。本版新项目使用当前配置；不将旧阶段记录解释成新版确认结果。
